# F11 — System accounts + funding

**Branch:** `feat/11-system-accounts-funding` · **Depends on:** F10

## Goal

Give money a legitimate way to enter and leave the system, closing the gap
left by F07 (accounts always open at zero).

## Scope

- `src/main/resources/db/migration/common/V4__system_accounts.sql` —
  seeds one `SYSTEM`-type account for a fixed, curated set of currencies
  (see design note — not "every currency `MoneyNormalizer` would accept",
  which is the full ISO-4217 registry and not enumerable in a migration).
- `AccountRepository.findByAccountTypeAndCurrency(AccountType, String)` —
  a Spring Data derived query, `Optional<Account>`.
- `TransferService.deposit(UUID accountId, BigDecimal amount, String reference)`
  and `.withdraw(...)` — both look up the target account's own currency,
  find the matching `SYSTEM` account, and delegate to `execute` with
  `kind = DEPOSIT` / `WITHDRAWAL`. **No second write path.**
- `UnsupportedCurrencyException extends BusinessRuleException` (422) — no
  `SYSTEM` account exists for the requested currency.
- `AccountController` gains `POST /api/v1/accounts/{id}/deposits` → 201
  (`{amount, reference?}`) and `POST /api/v1/accounts/{id}/withdrawals` →
  201, alongside the existing `/api/v1/accounts/{id}/*` routes.

## Explicitly not in this feature

- No idempotency key requirement yet (F14) — same temporary gap as F10,
  closed in the same later feature.
- No currency field on the deposit/withdrawal request — see design note.

## Design notes

- **No `currency` field on the request, and no enumerable "every supported
  currency" migration.** The original framing assumed a fixed, enumerable
  set of "supported currencies" a migration could seed one row per — but
  `MoneyNormalizer` (F05) validates against the full `java.util.Currency`
  / ISO-4217 registry (~180 codes) by design, not a whitelist, and an
  account can already be opened in any of them (F07). Two consequences,
  resolved here:
  - **The request has no `currency` field.** A deposit or withdrawal is
    always in the target account's own currency — there is no FX
    conversion (explicitly out of scope, see the roadmap index), so
    asking the caller to redundantly restate it only invites a spurious
    `CurrencyMismatchException` if it doesn't match. The service reads
    the account's currency directly.
  - **The migration seeds a curated, fixed list — USD, EUR, GBP, JPY** —
    covering the zero-decimal (JPY) and two-decimal (the rest) cases
    already exercised elsewhere in the test suite, not an attempt to
    enumerate every ISO-4217 code. An account can still be opened in any
    valid currency (e.g. KWD); funding one outside the seeded list
    returns a clear 422 via `UnsupportedCurrencyException` rather than
    silently creating a `SYSTEM` account on demand. On-demand creation
    was considered and rejected: it would need its own concurrency-safety
    story (two simultaneous first deposits in a novel currency racing to
    create the same `SYSTEM` row) for a case that doesn't otherwise arise
    in this project's scope.
  - Literal UUIDs are hardcoded for each seeded row (e.g.
    `00000000-0000-0000-0000-000000000001`) rather than generated by a
    DB function — Postgres uses `gen_random_uuid()`, H2 uses
    `RANDOM_UUID()`, and neither name is portable, so a literal avoids the
    split entirely for a `common/` migration.
- Routing deposits and withdrawals through the exact same `execute` method
  as transfers is the point of this feature, not an implementation detail:
  it means there is exactly one place in the codebase where a balance is
  ever mutated and a ledger entry is ever written, so every invariant F09
  established (locking, atomicity, the balanced-ledger guarantee) applies
  to funding for free.
- **Known scaling limit, accepted for now:** the per-currency SYSTEM
  account is a single row that every deposit and withdrawal in that
  currency locks, making it the first real throughput ceiling in the
  system. At this project's scale that's fine. If it ever isn't, the fix
  is sharding into several rows per currency (`SYSTEM/USD/0`,
  `SYSTEM/USD/1`, ...), chosen by hash, and summed for reporting — not
  redesigning the write path.
- No explicit uniqueness constraint added for "at most one `SYSTEM`
  account per currency" — Spring Data's `findByAccountTypeAndCurrency`
  returns `Optional<Account>`, and a single-result derived query already
  throws `IncorrectResultSizeDataAccessException` if more than one row
  ever matches, which is enough of a safety net given nothing in this
  feature creates `SYSTEM` accounts dynamically.
- **`AbstractIntegrationTest`'s per-test cleanup (F09) now re-seeds the
  `SYSTEM` accounts after every test, rather than special-casing them out
  of the delete.** The first attempt preserved existing `SYSTEM` rows and
  only reset their balance — but F09's and F10's tests each created their
  *own* throwaway `SYSTEM/USD` account for their own purposes, and once
  those stopped being deleted, they coexisted with F11's seeded
  `SYSTEM/USD` row and made `findByAccountTypeAndCurrency` throw
  `IncorrectResultSizeDataAccessException` (two results for one). Rather
  than auditing every test that creates an ad-hoc `SYSTEM` account for a
  currency collision — fragile, and only as good as the last person to
  remember it — cleanup now deletes every account, `SYSTEM` included, and
  re-inserts the same four seed rows every time. F09's and F10's
  `fundedAccount` test helpers were also simplified to call
  `TransferService.deposit` directly instead of hand-rolling a `SYSTEM`
  account, now that a real seeded one always exists to fund through.

## Verification

```bash
./gradlew build
```

Integration test: deposit into a fresh account, confirm the balance moves
and `SUM(ledger_entry.amount)` across the whole table is still exactly
zero (the SYSTEM account's matching debit is what keeps it there).
Withdrawal below the account's balance → 422 via the same insufficient-
funds path as a regular transfer. Deposit into an account whose currency
has no seeded `SYSTEM` account (e.g. KWD) → 422
`UnsupportedCurrencyException`.

## Review focus

- That the SYSTEM account is genuinely the *only* row exempt from
  `account_no_overdraft`, and that no code path lets a `CUSTOMER` account
  reach it directly instead of through `execute`.
- That deposit/withdrawal really do route through `TransferService.execute`
  and not a parallel balance-mutation path.
